# 全球高增长产品机会日报

一个低成本、零第三方 Python 依赖的产品机会雷达。它从多个国家和地区的 App Store、Steam、itch.io 榜单与公开讨论中寻找需求已验证、增长快、实现边界清晰且适合小团队差异化切入的产品，每天分别输出 App Top 8、手游 Top 6、非手游 Top 6，通过 GitHub Pages 发布并向飞书群推送摘要。

## 它现在会做什么

- 覆盖 12 个 App Store 市场的 App 免费榜、付费榜，以及游戏免费榜、畅销榜；
- 非手游汇总 Steam 热销、热门新品、即将推出榜，以及 itch.io 的 Web、Windows、macOS、Linux 热门与新品热榜；
- 页面按 App、手游、非手游三个 Tab 切换，支持手机、键盘导航和分类直达链接；
- 通过 Apple 元数据补充评分、评论量、类别、描述、发布日期和更新时间；
- 同时监控近 48 小时 Hacker News 产品精确提及与品类主题热度；
- 将快照保存到 SQLite，按相同国家与榜单计算 1、3、7、14、30 日配对增速；
- App、手游和非手游分别标准化与排名；非手游在合格候选中兼顾 Steam 和 itch.io，并按标题去重；
- 将候选分成“已验证机会”和“新发现观察”，已被多个时间窗口确认的产品优先展示；
- 每个分榜固定保留 2 个“早期苗头”名额，寻找刚上线/待上线、首次露头、评价基数低但已有抬升的产品；
- 计算同主题成熟竞品密度与单品饱和度，竞争越拥挤，最终机会分和早期分越低；
- 可借鉴度拆成需求验证、开发可行、跨市场迁移、分发可达、法律与合规安全五个维度；
- 政府或机构专属、高合规、博彩/真钱、成熟 IP、强网络效应和大型制作产品使用硬门槛排除；
- 最终分数使用可借鉴度乘数校准，不再允许增长热度掩盖实现与法律风险；
- 自动聚合同类机会主题，并为每个候选生成目标用户、MVP、变现、差异化和先验证风险；
- 自动回测 7、14、30 天前的入选产品是否继续增长，输出历史命中率；
- 数据源区分健康、降级和失败，降级市场不参与当天增速；
- 同一天重复运行会覆盖同一个 run，不重复积累快照；
- 每份报告包含 run ID 和数据指纹，可以追溯到对应数据库快照；
- 按日保存最近 45 天 HTML 与 JSON 历史报告，并在 Pages 中提供归档入口；
- 对数据量异常下降的数据源自动降级，避免不完整榜单参与增速计算；
- 飞书发送遇到限流、服务端错误或网络中断时自动重试，同日成功后不重复推送；
- 工作流任一阶段失败时，会向飞书发送包含 Actions 日志链接的红色告警；
- 生成适合桌面和手机阅读的响应式 HTML 报告。

这是一套“发现产品机会”的系统。可借鉴指需求、核心机制、目标用户和商业模式可被重新验证，不代表复制名称、美术、代码、品牌或其他受保护内容。公开榜单也无法提供精确下载量与收入，因此报告不会把潜力分伪装成商业数据估算。

## 本地运行

要求 Python 3.11 或更高版本，无需安装依赖：

```bash
python3 -m unittest discover -s tests -v
python3 -m app_radar --config config.json
```

生成文件：

```text
data/radar.db          历史快照
reports/latest.html    最新 HTML 日报
reports/latest.txt     最新纯文本日报
reports/latest.json    最新结构化结果
reports/archive/       最近 45 天 HTML/JSON 历史日报与索引
```

本地预览：

```bash
python3 -m http.server 8000 --directory reports
```

然后访问 `http://127.0.0.1:8000/latest.html`。

默认显示 App，可用 `#mobile_game`、`#non_mobile_game` 直达另外两个 Tab；例如 `latest.html#non_mobile_game`。新生成的历史日报也支持 Tab；禁用 JavaScript 时会完整显示各榜单。

## GitHub Pages 与飞书通知

`.github/workflows/daily-radar.yml` 已设置每天北京时间 08:17 主触发、10:17 备用触发，也支持手动触发。备用触发会先检查当天是否已有成功记录，有则跳过；检查异常时会继续运行，以避免漏报。手动触发始终执行。工作流会把完整日报和历史归档发布到 GitHub Pages，然后向飞书群发送 App、手游、非手游三个分榜各 Top 3 的卡片摘要和完整报告链接。失败时会发送独立告警；成功通知按报告日期去重。

在仓库的 Actions secrets 中配置 `LARK_WEBHOOK_URL`。实际 Webhook 只存放在 Secret 中；代码、工作流和日志都不包含它。

GitHub Actions cache 会保存 SQLite 历史、日报归档和飞书发送状态；报告和数据库也分别作为 30 天 artifact 上传，便于恢复。数据库与 Pages 归档默认保留 45 天，避免长期膨胀。首次运行是冷启动基线；之后依次启用 1、3、7、14、30 日变化与回测。超过 7 天没有运行时缓存可能被清理，报告会明确重新进入历史积累状态。

### 可选：需要准点时使用外部免费定时器

GitHub 的 `schedule` 是尽力调度，可能延迟。双时段机制降低漏跑概率，但不保证每天成功触发或 08:17 准点。如果需要更稳定的触发，可在 cron-job.org、Cloudflare Workers Cron 或同类服务中每天调用：

```text
POST https://api.github.com/repos/mjy0808/RankNest/actions/workflows/daily-radar.yml/dispatches
Authorization: Bearer <GITHUB_FINE_GRAINED_TOKEN>
Accept: application/vnd.github+json
Content-Type: application/json

{"ref":"main","inputs":{"force":"false"}}
```

Token 只需该仓库的 Actions 写权限，并且只存放在外部调度服务的 Secret 中，不能写入仓库。`force=false` 会复用当天去重检查；GitHub 后续触发的主任务和备用任务会检测到已有成功记录并跳过。网页中手动运行默认 `force=true`，因此仍可强制重新生成。外部触发属于可选配置；不配置时仍使用现有主触发和备用触发。

真正启动每日推送需要：

1. 在仓库 Settings → Pages 中选择 GitHub Actions 作为发布源；
2. 在 Actions secrets 中填写 `LARK_WEBHOOK_URL`；
3. 在 Actions 页面手动运行一次 `Daily app and game radar`；
4. 确认 Pages 报告可访问，且飞书群收到摘要卡片。

## 调整覆盖与评分

市场、榜单、候选数量、早期保留名额和并发量均在 `config.json` 中。默认三个榜单各保留 2 个早期名额；综合上线时间、低评价基数与首次露头等证据，早期信号达到分榜阈值且未命中硬风险的候选才有资格使用这些名额。App、非手游的早期阈值为 62，信号更稀疏的手游为 58。itch.io 新品热榜可提供发现信号，但不视为已验证增长。三个分榜使用不同基础权重，并在各自候选池内做百分位标准化；随后使用可借鉴度和竞争度乘数校准，并把已确认增长的候选排在普通单日新发现之前：

```text
App：排名 30% + 口碑 20% + 讨论 5% + 市场 10% + 新鲜度 10% + 可借鉴性 25%
手游：排名 35% + 口碑 20% + 市场 10% + 新鲜度 10% + 可借鉴性 25%
非手游：排名 35% + 口碑 20% + 市场 10% + 新鲜度 15% + 可借鉴性 20%
```

常规候选中，App 与手游要求可借鉴度至少 72，非手游至少 70；早期名额把门槛降到 App/非手游 58、手游 55，用较低确定性换更早发现，但仍执行完全相同的法律、IP、合规、网络效应和制作规模硬门槛。早期分综合上线时间、首次进入监控、低评价基数、短期动量、多市场露头与讨论信号；竞争分综合单品评价饱和度和同主题成熟竞品数量。itch.io RSS 的 `plainTitle` 用于跨来源标题去重，`createDate` 作为上线时间参考，`updateDate` 单独记录；缺少创建日期时不会把更新日期当作首次上线。未提供的评分、评价量不会填成已知数据；页面标记为“未提供”和“竞争待核实”，JSON 使用 `null`，竞争乘数取中性值。如果某个市场临时失败，其他数据源会继续运行，失败原因会进入报告。只有全部采集器都没有返回候选时，任务才会失败。

JSON schema 为 v6，非手游分榜键名为 `non_mobile_game`；加载历史数据库时兼容旧的 `steam_game` 分类。`steam.enabled` 和 `itch.enabled` 可以分别关闭来源，`report.non_mobile_game_count=0` 可关闭整个非手游 Tab（同时设置早期名额为 0）。覆盖范围取决于这些来源，并非全平台完整游戏库。

`health` 配置用于识别“请求成功但数据不完整”的情况：各来源设置绝对候选下限，并将不足上一个健康快照 65% 的来源标记为降级。采集器也会继续检查单个榜单为空或解析数量过低的情况。PR 会运行单元测试，并从 GitHub runner 执行不发布报告、不发通知的游戏来源连通性检查；外部来源失败会单独显示。

## 数据源边界

- Apple RSS 与 Lookup：公开接口，适合榜单与商店元数据；
- Steam 商店搜索：PC/桌面游戏的热销、热门新品和即将推出榜；
- itch.io [官方 RSS](https://itch.io/docs/api/overview#rss-feeds)：按 Web/桌面平台读取热门和新品热榜；不采集仅 Android/iOS 的项目，不将平台维度当作不同国家。RSS 可能临时不可用，失败会进入数据源状态；
- Hacker News Algolia：结合完整产品名精确匹配和 AI、效率、隐私、影像、教育、开发工具等品类主题热度，只作为辅助讨论信号；
- 暂未直接采集 Google Play 竞品数据，因为 Google 官方开发者 API 主要面向自己账号下应用的发布和管理。后续可按需要增加合规的第三方数据源。
